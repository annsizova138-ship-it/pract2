# dep-graph - граф зависимостей пакетов Ubuntu (вариант 20)

## 1. Общее описание

Инструмент командной строки для анализа и визуализации графа зависимостей
пакетов менеджера пакетов apt (Ubuntu). Готовые менеджеры пакетов и
библиотеки для получения зависимостей не используются: индекс репозитория
скачивается и разбирается самостоятельно (`urllib`, `gzip`, `lzma`).

Выполнены этапы 1-3 (параметры, сбор данных, граф) и **этап 4 -
дополнительные операции**: вывод порядка загрузки зависимостей и сравнение
его с настоящим менеджером пакетов.

## 2. Описание всех функций и настроек

| Параметр | Описание | По умолчанию |
|---|---|---|
| `--package ИМЯ` | имя анализируемого пакета (обязательный). В режиме `url` - как в apt: строчные латинские буквы, цифры, `+ . -`; в режиме `test` - большие латинские буквы | - |
| `--repo ПУТЬ` | URL репозитория (`http://` или `https://`) или путь к файлу тестового репозитория (обязательный) | - |
| `--repo-mode РЕЖИМ` | `url` - настоящий репозиторий, `test` - файл тестового репозитория | `url` |
| `--ascii-tree` | флаг: вывести зависимости в виде ASCII-дерева (появится на этапе 5) | выключен |
| `--max-depth N` | максимальная глубина анализа, целое число не меньше 1 | 3 |
| `--filter ПОДСТРОКА` | не учитывать пакеты, в имени которых есть подстрока (без пробелов) | не задана |
| `--load-order` | вывести порядок загрузки зависимостей вместо графа | выключен |

Все параметры проверяются до начала работы. Ошибки выводятся в stderr в
виде `Ошибка параметров: ...`, программа завершается с кодом 2:

- не задан `--package` или `--repo`;
- недопустимое имя пакета для выбранного режима;
- `--repo-mode` не равен `url` или `test`;
- в режиме `url` адрес не начинается с `http://` или `https://`;
- в режиме `test` файл не найден;
- `--max-depth` - не целое число или меньше 1;
- `--filter` содержит пробелы;
- неизвестная опция.

Коды завершения: `0` - успех, `1` - ошибка работы (репозиторий недоступен,
пакет не найден, граф или изображение построить не удалось), `2` - ошибка
параметров командной строки.

**Формат данных apt и прямые зависимости.** Адрес `--repo` указывает на файл
`Packages` (`.gz`, `.xz` или без сжатия), например `http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/Packages.gz`.
Зависимостями считаются имена из полей `Depends` и `Pre-Depends`; версии и
архитектуры отбрасываются, из альтернатив `a | b` берётся первая, пакет,
которого нет в индексе (например, виртуальный), - пакет без зависимостей.

**Построение графа.** Обход в ширину (BFS) реализован рекурсивно: функция
раскрывает один уровень пакетов (находит их прямые зависимости) и вызывает
саму себя для следующего уровня. Каждый пакет раскрывается один раз, поэтому
общий пакет (например, `D` в «ромбе») попадает в граф один раз, а
циклические зависимости не приводят к зависанию.

- **Глубина** (`--max-depth N`): корень лежит на уровне 0, его прямые
  зависимости - на уровне 1. Пакеты на уровне N попадают в граф, но их
  зависимости не раскрываются.
- **Фильтр** (`--filter ПОДСТРОКА`): пакеты, в имени которых есть подстрока
  (с учётом регистра), не учитываются вообще: ни как вершины, ни как рёбра.
  Если подстрока есть в имени самого анализируемого пакета, это ошибка.
- **Циклы**: находятся поиском в глубину и выводятся в виде `A -> B -> A`.

**Тестовый репозиторий** (`--repo-mode test`). Вместо URL указывается файл
с описанием графа: по одной строке `ПАКЕТ: зависимости через пробел`.
Имена пакетов - большие латинские буквы. Пустые строки и комментарии
(от `#` до конца строки) пропускаются. Пакет, упомянутый только как
зависимость, считается пакетом без зависимостей.

```
# examples/diamond.txt
A: B C
B: D
C: D
D:
```

**Порядок загрузки** (`--load-order`). Порядок, в котором нужно установить
пакеты, чтобы каждая зависимость оказалась раньше пакета, которому она
нужна. Используется обход графа в глубину: пакет записывается после всех
своих зависимостей, корень всегда последний. Глубина и фильтр действуют так
же, как при построении графа. Для цикла верного порядка не существует:
связь, замыкающая цикл, пропускается, а цикл выводится отдельно.

Файлы проекта:

```
src/        исходный код
tests/      модульные тесты (unittest)
examples/   тестовые репозитории (файлы с описанием графов)
scripts/    скрипты Windows (.bat): запуск тестов и демонстрации
run.bat     быстрый запуск: run.bat --package ... --repo ...
```

## 3. Команды для сборки проекта и запуска тестов

Сборка не требуется. Нужен Python 3 (разработано на версии 3.10); сторонние
библиотеки не нужны, используется только стандартная библиотека.

Запуск тестов (из корня репозитория):

```
# Windows
scripts\run_tests.bat

# Linux / macOS / Git Bash
PYTHONPATH=src python3 -m unittest discover tests
```

Запуск приложения:

```
python src/main.py --package wget --repo http://archive.ubuntu.com/ubuntu/dists/noble/main/binary-amd64/Packages.gz --max-depth 20 --load-order
python src/main.py --package A --repo examples/diamond.txt --repo-mode test --load-order
```

Демонстрации (Windows): `scripts\demo_load_order.bat` (тестовые
репозитории), `scripts\demo_real_load_order.bat` (настоящий репозиторий,
нужен интернет), а также демонстрации этапа 3.

## 4. Примеры использования

Ромб: общий пакет `D` раньше `B` и `C`, корень последний:

```
python src/main.py --package A --repo examples/diamond.txt --repo-mode test --load-order
```

```
Порядок загрузки пакета A (зависимости раньше зависимых):
  1. D
  2. B
  3. C
  4. A
Циклические зависимости: нет
```

Цикл (порядок строится, цикл выводится отдельно):

```
python src/main.py --package A --repo examples/cycle.txt --repo-mode test --load-order
```

```

  1. D
  2. C
  3. B
  4. A
Зависимости не раскрыты (глубина): D
Циклические зависимости:
  A -> B -> C -> A
```

  4. H

### Сравнение порядка загрузки с настоящим менеджером пакетов

Эталон - `apt-get` в режиме имитации (`-s`) на «пустой» системе, чтобы в
список попали все пакеты, а не только отсутствующие:

```
apt-get -s -o Dir::State::status=/dev/null -o APT::Install-Recommends=false install curl | grep ^Inst
```

(Ubuntu нужна той же версии, что и в URL; для `noble` - 24.04. Перед
запуском выполните `sudo apt update`.) Результат для индекса `noble/main`:

| Пакет | Пакетов у нас | Пакетов у apt | Порядок |
|---|---|---|---|
| `nano` | 6 | 6 | совпал полностью |
| `wget` | 11 | 11 | отличается, оба порядка допустимы |
| `curl` | 36 | 32 | отличается, оба порядка допустимы |

Расхождения и их причины:

1. **Порядок не единственный.** Для графа без циклов существует много
   допустимых порядков (любой, где зависимость идёт раньше зависимого).
   Мы выводим обход в глубину в порядке перечисления зависимостей; `apt`
   использует собственный алгоритм упорядочивания. Проверка показала, что
   порядок `apt` для всех трёх пакетов удовлетворяет нашему графу, кроме
   одной связи из цикла (см. п. 3).
2. **Виртуальные пакеты.** У `curl` четыре лишних пакета: `libssl3`,
   `libgnutls30`, `libnettle8`, `libhogweed6`. В индексе Ubuntu 24.04 их
   реальные пакеты называются `libssl3t64` и т. д. и объявляют
   `Provides: libssl3 (= ...)`. Мы не обрабатываем `Provides`, поэтому имя
   остаётся «листом»; `apt` подставляет реальный пакет и в список установки
   виртуальное имя не попадает.
3. **Цикл `libc6` <-> `libgcc-s1`.** `libc6` зависит от `libgcc-s1`, а
   `libgcc-s1` от `libc6`. Порядка, который бы удовлетворил обе связи, нет.
   Мы разрываем цикл на повторно встреченном пакете и сообщаем о цикле, `apt`
   разрывает его по своим правилам; в обоих порядках для проверенных пакетов
   `libgcc-s1` оказывается раньше `libc6`.
4. **Альтернативы и состояние системы.** Мы всегда берём первую альтернативу
   `a | b`, а `apt` выбирает подходящую по версиям, приоритетам и тому, что
   уже установлено. На непустой системе `apt` пропускает установленные
   пакеты.
